## 1. Executive Summary & Goals

Product Forge requires vector and lexical retrieval across two fundamentally distinct operational contexts:
1. **Product Forge Platform Itself:**
   - **PF-SB (Sovereign Bundle / Local / Community Edition):** Air-gapped single-binary environments where zero external daemons (no PostgreSQL, no Docker) exist. Operates on embedded SQLite with vector capability (`sqlite-vss` or pure-Go embedded cosine similarity).
   - **PF-PG (Enterprise Edition):** Cloud and SaaS Kubernetes clusters operating against PostgreSQL 16+ with the `pgvector` extension and Row-Level Security (RLS) tenant isolation.
2. **Product Forge Generated Products (PF-GP):**
   - Products designed and generated by Product Forge (e.g. documentation AI assistants, engineering agents, internal tools) declare their retrieval requirements in `product-manifest.yaml` (per Sections 18–21 of `docs/Product_Forge_RAG_CAG_Knowledge_Fabric_Integration.md`).
   - Generated products require a unified datastore adapter interface so their application logic remains identical whether deployed as an embedded desktop utility (SQLite backend) or a cloud-hosted multi-tenant SaaS application (PostgreSQL pgvector backend).

`BI-PF-1552` provides this canonical dual-engine implementation behind `datastore.MemoryRepository` in Go (Rule 17).

## 2. Core Architectural Principles

1. **Provider-Neutral Interface:** All memory operations implement `datastore.MemoryRepository`:
   ```go
   type MemoryRepository interface {
       Put(ctx context.Context, e MemoryEntry) (MemoryEntry, error)
       Get(ctx context.Context, id string) (MemoryEntry, error)
       Search(ctx context.Context, q string, scope MemoryScope, k int) ([]MemoryEntry, error)
       Delete(ctx context.Context, id string) error
   }
   ```
2. **Dual-Backend DSN Auto-Dispatch:**
   - Connection strings starting with `sqlite://`, `file:`, or a local `.db` path instantiate `SqliteMemoryStore`.
   - Connection strings starting with `postgres://` or `postgresql://` instantiate `PgMemoryStore`.
3. **Resilient Local Fallback for PF-SB:**
   - In environments where the native `sqlite-vss` dynamic library extension cannot be compiled or loaded (e.g., restricted Windows environments, stripped air-gapped containers), `SqliteMemoryStore` gracefully falls back to embedded pure-Go vector indexing and cosine distance evaluation while maintaining full SQLite transactional metadata persistence.
4. **Strict Isolation & Security:**
   - Multi-tenant boundary checks (`TenantID`, `Project`, `Source`, `User`, `ACL`) apply in SQL/storage predicates before results are returned. Zero cross-tenant leakage.

## 3. Detailed Component Design

### 3.1 Package `go/dualvec`

The implementation resides in `go/dualvec` and implements `datastore.MemoryRepository`:

```text
go/dualvec/
├── dualvec.go          # Top-level factory (NewMemoryRepository), configuration, and DSN parser
├── sqlite_store.go     # SQLite-backed implementation (metadata table + vector similarity index)
├── pg_store.go         # PostgreSQL + pgvector adapter (reusing/wrapping edpdata.MemoryStore)
└── dualvec_test.go     # Conformance test suite running identical test vectors against both backends
```

### 3.2 Backend 1: SQLite Vector Store (PF-SB & Local Generated Products)

* **Zero-CGO Pure-Go Portability:**
  - Operates using `modernc.org/sqlite` (pure Go, CGO-free).
  - Embeddings are serialized as packed little-endian 32-bit float blobs (`1536 * 4 = 6144` bytes).
  - Dot product and L2 norm calculations run in SIMD-friendly pure-Go loops without heap allocations per vector comparison.
  - Hybrid scoring fuses content token matching with cosine distance:
    $$\text{Score} = 0.7 \times \text{CosineSimilarity} + 0.3 \times \text{LexicalMatch}$$
  - Uniqueness and Data Invariants: Primary key on `memory_entries(id)` prevents duplicates; vectors $\ne 1536$ dimensions are rejected before disk write.
  - Backup & Recovery: Backed up via standard SQLite `VACUUM INTO '<backup_path>'` or file snapshotting.

* **Schema:**
  ```sql
  CREATE TABLE IF NOT EXISTS memory_entries (
      id TEXT PRIMARY KEY,
      tenant_id TEXT NOT NULL,
      project_id TEXT,
      kind TEXT NOT NULL,
      object_ref TEXT,
      acl_scope TEXT,
      content TEXT,
      source TEXT,
      owner TEXT,
      embedding BLOB,
      created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
      updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  );
  CREATE INDEX IF NOT EXISTS idx_mem_tenant_proj ON memory_entries(tenant_id, project_id);
  CREATE INDEX IF NOT EXISTS idx_mem_owner ON memory_entries(owner);
  ```

### 3.3 Backend 2: PostgreSQL pgvector Store (PF-PG & Enterprise Generated Products)

* Connects to PostgreSQL using standard `datastore.RelationalStore`.
* Operates under restricted application role (`pf_app_user`) with `BYPASSRLS` revoked to guarantee strict multi-tenant Row-Level Security.
* Leverages `0015_memory_repository.up.sql` schema:
  - Generated `tsvector` with GIN indexing for high-speed lexical search.
  - Optional `vector(1536)` column with HNSW / IVFFlat indexing for cosine distance (`<=>`).
  - Strict tenant boundary isolation via session context (`app.tenant_id`).

### 3.4 Backend 3: PF-GP Generated Product Configuration

Generated products specify vector and memory preferences in their product manifest:
```yaml
knowledge:
  retrieval:
    enabled: true
    strategy: hybrid
    vector: true
database:
  engine: auto # auto resolves to sqlite for local desktop or postgres for SaaS
  dsn: "${DATABASE_URL:-sqlite://./data/agent_memory.db}"
```
The generated product executes:
```go
repo, err := dualvec.New(dualvec.Config{
    DSN: cfg.Database.DSN,
    Dimension: 1536,
})
```
No product business logic changes between local community deployment and multi-tenant enterprise deployment.

## 4. Availability, Resilience & Observability

### 4.1 Availability & Fail-Closed Errors
- **Startup Connection Verification:** On initialization, `dualvec.New` verifies store health (`PingContext`). Unreachable databases fail closed with typed error `ErrStorageUnavailable`.
- **Context Timeouts:** All queries accept `context.Context` and enforce caller/server timeouts.

### 4.2 Observability & Metrics
- **Structured Logs:** Emitted on query execution with tags: `engine` (sqlite|postgres), `tenant`, `project`, `operation`, `duration_ms`.
- **Prometheus Metrics:**
  - `dualvec_operations_total{engine, op, status}`: Counter tracking requests and success/failure.
  - `dualvec_duration_seconds{engine, op}`: Histogram tracking query latency.
  - `dualvec_dimension_errors_total`: Counter tracking rejected vector writes.

## 6. Test & Verification Plan

1. **Shared Conformance Suite:**
   A test function `runMemoryConformanceSuite(t *testing.T, repo datastore.MemoryRepository)` executes against both `SqliteMemoryStore` and `PgMemoryStore`:
   - Validates all 8 canonical memory types (`raw_evidence`, `semantic`, `episodic`, `decision`, `procedural`, `failure`, `policy`, `working`).
   - Verifies dimension enforcement (rejects vectors $\ne 1536$).
   - Verifies ACL scope filtering (`private` entries visible only to `Owner`).
   - Four negative leakage tests proving zero cross-tenant and cross-project leakage.
   - Vector similarity ordering: verifies that nearest vectors achieve highest rank.
2. **Pure-Go Fallback Verification:**
   - Proves SQLite store executes correctly without external C dynamic libraries.
3. **Packaging Integration:**
   - Wires `dualvec.New` into `edpsvc` memory route and verify build under `go test ./...`.
