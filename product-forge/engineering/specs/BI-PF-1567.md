## 7. Functional requirements
### FR-1 — Govern every memory operation
- **priority:** P0
- **source:** BI-PF-1567
- **preconditions:** Canonical MemoryRecord and datastore.MemoryRepository exist.
- **trigger:** Authenticated memory operation enters edpsvc.
- **inputs:** authenticated Scope; operation payload; server-resolved principal
- **outputs:** scoped result; non-leaky denial; bounded metrics/audit
- **errors:** ErrInvalidScope; validation error; ErrNotFound; store error; ErrLimitExceeded
- **auth:** Scope and ACL are enforced server-side; caller authority fields are rejected on mismatch.
- **idempotency:** Put is idempotent by record ID for the same tenant/project/owner.
- **data_rules:** Canonical validation then tenant/project/ACL filters.
- **edge_cases:** missing project; invalid kind; oversized payload; store unavailable
- **acceptance:** Given an authenticated memory operation, when it enters edpsvc, then it is validated, scoped, and routed through the orchestrator; a static test forbids direct repository bypass.
- **verification:** go test ./... in go/pfmemory; go test ./... in go/edpsvc

### FR-2 — Deny cross-boundary access
- **priority:** P0
- **source:** BI-PF-1567
- **preconditions:** Records from multiple tenants/projects exist.
- **trigger:** Read, search, write, or delete targets another tenant/project or private owner.
- **inputs:** Scope; record target; search query
- **outputs:** ErrNotFound on denial
- **errors:** ErrNotFound
- **auth:** Tenant, project, ACLScope, and owner must match before any data or mutation is returned.
- **idempotency:** Denied operations have no side effects.
- **data_rules:** Tenant/project filters plus post-read authorization.
- **edge_cases:** cross-tenant ID read; cross-project ID delete; private owner mismatch; project-empty legacy row
- **acceptance:** Given a cross-boundary request, when executed, then no data is returned or mutated; search revalidates every hit and delete is read-verify-delete.
- **verification:** go test ./... in go/pfmemory; go test -race ./... in go/pfmemory

### FR-3 — Prove leakage resistance under concurrency
- **priority:** P0
- **source:** BI-PF-1567
- **preconditions:** Fake and real repository adapters are available in tests.
- **trigger:** Four negative leakage suites run concurrently.
- **inputs:** concurrent cross-tenant requests; concurrent cross-project requests; ACL denial requests; mixed load
- **outputs:** all suites pass under race detector
- **errors:** any exposure fails the test suite
- **auth:** All suites use server-resolved Scope only.
- **idempotency:** Concurrent reads do not mutate state; writes use unique IDs.
- **data_rules:** No test may bypass the orchestrator.
- **edge_cases:** same ID across tenants; same project name across tenants; private record collision; concurrent delete/read
- **acceptance:** Given four negative leakage suites, when run concurrently with -race, then all pass with zero exposure.
- **verification:** go test -race ./... in go/pfmemory; TestCrossTenantReadWriteSearch, TestCrossProjectReadWriteSearch, TestACLPrivateDenial, TestConcurrentBoundaryLoad

## 10. Non-functional requirements
- search k 1..100 with default 20
- operation timeout <= 5s
- zero cross-tenant/project leakage under -race
- no unbounded scans
- static bypass test fails direct repository calls

## 11. Data lifecycle
Existing memory rows are unchanged. Governed reads hide project-empty rows. New writes require project. No retention or schema change.

## 12. Compatibility
Allowed response shapes preserved; project-empty rows hidden; delete requires ScopedDeleter support and fails closed otherwise.

## 13. Rollback behavior
Revert the gateway wiring and restore the prior edpsvc binary. No schema or stored-data mutation.
